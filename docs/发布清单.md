# 发布清单

从「本机一个能跑的目录」到「GitHub 上一个有人能 clone 的仓库」，只走这一个文件。

发布前把 `binskyz` 全部替换成你的 GitHub 用户名：`.github/ISSUE_TEMPLATE/config.yml`、`package.json` 的 `repository` / `bugs` / `homepage`。检查一遍还有没有漏的：

```bash
grep -rn "binskyz" --include="*.md" --include="*.json" --include="*.yml" . | grep -v node_modules
```

## 一、本地验收（不通过就别往下走）

```bash
cd ~/.dsh/plugins-local/dsh-yunpa
node verify-release.mjs            # 8 项：必备文件/元数据/忽略规则/凭据扫描/语法/两半身导出/个人信息
node .github/scripts/check-templates.mjs   # 模板：tab、顶层键、issue form 的 type/id/label
node .github/scripts/check-doc-links.mjs   # 文档相对链接
node install.mjs --check           # 安装四件套
```

四条全绿再提交。任何一条红，都是「推到 GitHub 之后别人 clone 就出事」的那种红。

## 二、提交

```bash
cd ~/.dsh/plugins-local/dsh-yunpa
git init -b main
git add -A
git status --short          # 逐行看：不该出现 vault.bin / cft/ / shots/ / *.bak / api-token.txt
git commit -m "feat: dsh-yunpa 0.10.0 — 登录态抓取插件首个公开版本"
```

`git status` 那一步别跳。`.gitignore` 覆盖的是产物，不是你的判断——真漏了一个 `vault.bin`，历史里就洗不掉了。

## 三、建远端并推送

三种方式，按你手头有什么选：

### A. 有 `gh` CLI（最省事）

```bash
gh auth login                     # 走浏览器登录，凭据由 gh 自己管，不经过我
gh repo create dsh-yunpa --public --source=. --remote=origin --push
```

### B. 有 Personal Access Token

```bash
# 在 GitHub → Settings → Developer settings → Personal access tokens → Fine-grained
# 权限只要：Contents: Read and write；Administration: Read and write（要建仓库才需要）
git remote add origin https://<TOKEN>@github.com/binskyz/dsh-yunpa.git
git push -u origin main
git remote set-url origin https://github.com/binskyz/dsh-yunpa.git   # 推完立刻把 token 从 remote 里摘掉
```

Token 用完就 revoke。**不要**把它写进 `.git/config` 之后又忘记——那是最常见的泄漏点，`.git/config` 不会被 `.gitignore` 保护。

### C. 仓库已经在网页上建好了

```bash
git remote add origin https://github.com/binskyz/dsh-yunpa.git
git push -u origin main
```

## 四、发第一个版本

```bash
git tag -a v0.10.0 -m "dsh-yunpa 0.10.0"
git push origin v0.10.0
```

tag 一推，`.github/workflows/release.yml` 会自动做四件事：校验 tag 与 `package.json` 版本一致 → 跑发布验收 → `npm pack` → 建 Release 并挂上 `.tgz`。

跑完去仓库 **Releases** 页确认：有一个 `v0.10.0`，附件是 `dsh-yunpa-0.10.0.tgz`。

## 五、推完怎么验（别只看 Actions 是绿的）

1. **CI 页**：两个 job 都绿——`发布验收（Windows）`、`模板与文档（Linux）`。
2. **仓库首页**：README 能正常渲染，`docs/` 里的链接点得开。
3. **Issues → New issue**：能看到「Bug 报告」「功能请求」两个模板，点开是表单不是空白。
4. **干净 clone 一次**（这步最能抓漏）：

   ```bash
   cd /tmp && git clone https://github.com/binskyz/dsh-yunpa.git && cd dsh-yunpa
   node verify-release.mjs
   ```

   干净 clone 上能过，才说明「别人拿得到的东西」是完整的。

5. **装进一份新 profile**（可选，最接近真实用户）：

   ```bash
   # 把 clone 出来的目录换成 file: 依赖，然后 node install.mjs
   ```

## 六、出事怎么退

| 情况 | 动作 |
|---|---|
| 推错了文件 | `git rm --cached <file>` 后重提；若已推到远端，改写历史要 force push，唯一副本在手才做 |
| Release 发错版本 | 删 tag：`git push --delete origin v0.10.0` + `gh release delete v0.10.0`，改完重打 |
| 不想公开了 | 仓库 Settings 最底部 → Change visibility → Private（历史仍在，别指望「删了就没人有」） |
| 想整个重来 | 保留本地目录，远端删仓库重建；本地 `rm -rf .git` 重来一遍 |

## 七、这套模板里哪些是给「别人」看的

自己用不上的部分，是给将来提 issue 的人省时间：

- `bug_report.yml` 必填 `check-all.mjs` 输出 → 省掉「你能贴一下自检吗」这一轮往返
- `config.yml` 把「插件页看不见云爬」直接指到安装段 → 这类问题不会变成 issue
- `SECURITY.md` 列了「已知的非问题」 → 省掉「你们居然能读我 cookie」的误会
- `CONTRIBUTING.md` 写死「不引入运行时依赖」 → CI 会拦，不用靠人记
