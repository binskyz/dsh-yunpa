## 二、DSH 官方路线（master 分支，本机 0.2.1-rc.2 还没有）

[docs/subsystems/browser-use.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/browser-use.md)：内置 `browser-use` 子系统，Provider 可为 **Stagehand**（AI 辅助操作/观察/抽取），"launched browser belongs to the exact live Agent and Session, calls across turns reuse that browser"。升级到含该子系统的版本后，导航/点击/抽取可以交给官方，我的插件只留"凭据库 + 密码迁移 + 站点结构化提取"。

## 三、生态系统（非 DSH）

| 类别 | 项目 | 备注 |
|---|---|---|
| cookie 提取库 | `browser_cookie3`、`pycookiecheat` | Chrome 127+ 起对 v20 失效；`pycookiecheat` 无 Windows 支持 |
| 浏览器扩展 | Get cookies.txt LOCALLY（Netscape）、Cookie-Editor（JSON/含 HttpOnly） | 手工导出，最稳的兜底 |
| MCP | [playwright-mcp-server-custom](https://www.npmjs.com/package/playwright-mcp-server-custom)（支持 `setCookies` 预置登录态）、Chrome Devtools Advanced MCP（克隆真实 Chrome profile 复用登录态） | 思路同"复制 profile" |
| agent 浏览器 | agent-browser 的 `--profile` 命名会话、browser-use / Skyvern / Stagehand | 都是"一次人工登录，之后复用 profile" |

## 四、结论

1. **没人同时做这四块**：cookie 桥、人工登录流程、加密凭据库、**浏览器密码库迁移（v20）**。前三块各有人做过，第四块（`auth_pw_open` + `auth_pw_grab` 半自动迁移）生态里没有现成实现——因为 v20 一出来，大家的选择都是"让用户自己再登一次"。
2. **本机不适合直接装 dsh-browser**：`dsh plugin add` 在这套解包安装上会把 pnpm 指到 `resources\app\runtime\...`（不存在）；且它要求 dsh ≥0.1.5-rc.2 的全工作区构建。要装只能像我这样手工落 `node_modules` + patch。
3. **值得吸收的三个设计**（已/将落地）：
   - allowlist + 只走 127.0.0.1（cookie-bridge）→ 我的 cookie 只在本地加密库存，无外发；
   - `browser_wait_login` 的判定式等待（companion）→ 已改进 `auth_pw_grab` 的 `waitSec` 轮询；
   - 文本快照而非截图（dsh-browser）→ 我的 `auth_fetch kind=posts` 就是同一思路，只针对贴吧/NGA 定制。
